# Staff Web en Cloud Run

El portal usa React para la interfaz y Nginx para servir la SPA y enviar `/api/` a `finance-api` por HTTPS. Cloud Run proporciona el origen público. Staff Web requiere una versión de FastAPI con las rutas de sesión, soporte y auditoría.

## Primera publicación

1. Confirmar las ramas y fijar el SHA completo del frontend con ambos roles. Ejecutar `npm ci`, `npm run lint`, `npm run typecheck`, `npm test` y `npm run build` desde `staff-web/`. Desde la raíz del frontend, construir con `docker build --platform linux/amd64 --label "org.opencontainers.image.revision=$SHA" -t "$IMAGE" staff-web`. Usar el repositorio regional existente `finance-ai` y el nombre de imagen `staff-web:$SHA`.
2. Confirmar el estado de facturación y probar el prerrequisito de backend con el procedimiento de abajo. Para registrar el origen exacto, se puede crear primero `finance-staff-web` con IAM de invocación privado. Usar el digest publicado en Artifact Registry, `STAFF_API_HOST` con el hostname devuelto por `gcloud run services describe finance-api`, e identidad de ejecución dedicada sin roles adicionales. Configurar 1 vCPU, 256 MiB, 0–3 instancias, concurrencia 40, puerto 8080, facturación por solicitudes, sonda de inicio `/health` y `--invoker-iam-check`. Consultar el `status.url` de Staff Web y usar exactamente ese origen, sin barra final.
3. Tras la actualización autorizada de FastAPI, ejecutar `bash staff-web/deploy/verify-staff-api.sh "$API_URL" "$STAFF_URL"`. Si pasa, habilitar el acceso público de Staff Web mediante la política de invocación del nuevo servicio. FastAPI conserva la autorización de cada operación.
4. Ejecutar `bash staff-web/deploy/verify-staff-api.sh "$STAFF_URL" "$STAFF_URL"` y `node staff-web/deploy/verify-browser.mjs "$STAFF_URL"` desde la raíz del frontend, con Chromium instalado por Playwright. Los checks comprueban el proxy, la denegación de solicitudes anónimas o de otro origen y la carga de rutas/recursos en un navegador. Probar login, MFA, cookies, rol cruzado, sesión, tickets e informes con cuentas y registros de prueba ya autorizados. Usar un entorno aislado para cambios de tickets u otros datos de producción.

## Actualización necesaria de FastAPI

- Al promover un release de FastAPI a `main`, **Deploy to Google Cloud Run** se inicia cuando termina con éxito el CI del nuevo SHA. El workflow conserva la versión de MFA montada en producción. Para ejecución manual, indicar el SHA completo y la versión numérica aprobada de `finance-ai-staff-mfa-encryption-key`.
- Para un release con migraciones, registrar la revisión activa de Cloud Run, la revisión de Alembic y la hora UTC o LSN de Neon antes de fusionar a `main`. Crear y comprobar una rama de recuperación con vencimiento explícito, separada de la rama de ensayo. Ante una regresión de código, devolver el tráfico a la revisión sana y verificar la compatibilidad con el esquema aditivo. Ante pérdida o corrupción de datos, restaurar primero en una rama aislada, verificar conteos e integridad y conciliar las escrituras posteriores al punto de recuperación antes de cambiar la conexión de producción.
- El workflow incorpora el `status.url` exacto de Staff Web al allowlist existente. La cuenta de ejecución del backend tiene acceso al secreto de MFA. Mantener la misma clave mientras existan autenticadores cifrados con ella.
- El workflow actualiza la imagen y la configuración de Staff. Fija también `FINANCE_AI_STAFF_CLOUD_RUN_HOST` al hostname devuelto por `finance-api`, de modo que las cookies sigan siendo seguras tras la terminación TLS de Cloud Run. Verificar que la revisión preserve recursos, escalado, ingreso, cuenta de servicio, conexión de ejecución y sonda. La revisión inspeccionada tenía 1 vCPU, 512 MiB, concurrencia 80 y un máximo de 3 por revisión con máximo de servicio 20.
- Tras el release comprobar `/health/ready`, el contrato público vía `verify-staff-api.sh` y los controles de origen y cookies. La prueba anónima de refresh exige HTTPS válido según FastAPI y una respuesta 401 tras validar el origen. Mantener la validación de transporte y revisar la confianza en cabeceras del servidor ASGI si falla.

## Actualizaciones del portal

**Deploy Staff Web to Cloud Run** se inicia tras un push a `main` cuando **Staff web CI** aprueba ese commit. También se puede ejecutar manualmente desde `main`. Publica la imagen etiquetada con el SHA, despliega su digest sobre el servicio existente y verifica la revisión y su URL pública.

Workload Identity Federation restringe la autenticación al repositorio frontend, a `refs/heads/main` y al archivo de despliegue. La identidad de GitHub tiene escritura en el repositorio regional `finance-ai`, rol Cloud Run Developer sobre `finance-staff-web` y permiso para actuar como su cuenta de ejecución. El workflow obtiene el host de la API desde la configuración del servicio del portal.
